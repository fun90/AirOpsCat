# Fix Runtime Bug

## 目标

把一次运行时故障从“日志里有异常”推进到“代码已修复、接口已验证、必要时已发版部署”。优先保持变更小、验证真、现场可追溯。

## 基本流程

1. 读取用户提供的日志、附件、控制台输出或运行现象，先提取入口方法、异常类型、事务边界、请求路径和时间点。
2. 检查工作区状态。只修改和当前 bug 有关的文件，不回退用户已有变更。
3. 按项目规则选择代码探索方式：
   - 若项目存在并启用 `.codegraph/`，先用 `codegraph status`，必要时 `codegraph sync`，再用 `codegraph query/context/callers/callees/impact`。
   - 否则使用 `rg`、源码阅读和最小范围调用链追踪。
4. 先定位触发路径，再定位持久化、事务、序列化、权限、网络或配置等真实失败点。不要只按异常表面字符串改代码。
5. 做最小修复。优先复用现有仓储、服务和控制器模式；不要引入无关重构。
6. 本地验证。能启动服务时，优先走真实接口；不能启动时至少完成编译、单元测试或静态检查，并说明阻塞点。
7. 若用户要求发布/部署，按项目发版和部署技能执行，先确认 workflow 成功，再部署和验证服务状态。

## 日志定位

遇到堆栈时先看这些线索：

- 最内层 `Caused by`：真实异常类型和实体/字段/资源。
- 第一段业务代码栈：通常是 controller、service 或 repository 入口。
- 事务提交前异常：重点检查 flush 时的托管实体、bulk update/delete、级联关系、懒加载和已删除实体引用。
- 部署后回归：确认当前线上版本、tag、workflow 产物时间、服务启动日志和进程路径。

如果用户只贴一段日志，不要先要求补全；先用现有信息定位最大概率路径，再读代码验证。

## 修复原则

- 对 ORM 删除/更新问题，避免在同一事务里先加载带关联的实体，再 bulk delete 其关联目标。可改为按 id 原生 SQL/JPQL 清中间表或外键字段，减少持久化上下文残留。
- 对 controller 已有的业务校验，必要时下沉到 service，保证其他调用入口一致。
- 对中间表、多对多、历史表、统计表、主从表，先清依赖关系，再删主实体。
- 对生产配置或敏感主机，不在回复中回显完整地址、密钥或密码。
- 如果测试需要临时数据，使用明显前缀，记录 id，验证后清理。

## 本地接口测试

优先按项目已有方式启动：

1. 检查 MySQL/Redis 等依赖服务状态。
2. 确认应用配置中的默认库名、账号、端口。
3. 启动应用后先访问健康页、登录页或公开接口确认服务可用。
4. 若接口需要登录，使用本地临时账号或已有测试账号；不要修改真实用户密码。临时密码需要按项目同款加密方式生成。
5. 准备能覆盖 bug 的最小数据：
   - 触发关联清理的表要真实插入。
   - 能触发失败的边界字段要保留。
   - 避免无关字段触发额外错误。
6. 调真实 HTTP 接口，记录状态码、响应体、数据库清理结果和新增日志。
7. 验证日志中不再出现目标异常；若出现新异常，区分是否由测试数据不合法导致。
8. 清理临时用户、临时业务数据和本地进程。

## Git 与发布

- 未经用户要求，不提交、不推送、不部署。
- 用户要求“提交已跟踪代码”时，只提交已跟踪变更，不加入未跟踪文件。
- 提交信息遵循项目 Conventional Commits 规则，描述使用简体中文，不加 AI 署名。
- 重新发布版本时，先确认 `pom.xml` 版本、当前 `HEAD`、本地/远端 tag、分支是否已 push。
- 等 GitHub workflow 完成且结论为 success 后，再部署 release 产物。
- 部署后至少验证：
  - 安装命令退出码为 0。
  - systemd 服务为 `active`。
  - 启动日志包含目标版本。
  - 进程命令指向预期部署路径。

## 汇报格式

最终回复保持短而完整：

- 说明根因和修复点。
- 列出关键验证结果，尤其是接口状态码、数据库结果、日志中目标异常是否消失。
- 说明未执行或被阻塞的验证原因。
- 若进行了 Git/发布/部署，给出提交、tag、workflow 和服务状态。
