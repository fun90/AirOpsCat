## Context

当前系统已收敛为 sing-box 单内核，节点部署配置由 `DeploymentDataLoader` 和 `SingBoxConfigBuilder` 根据节点、账户、路由规则及系统配置即时生成，并通过 SSH 写入固定路径 `/etc/sing-box/config.json`。远端校验和重启成功后，`CoreDeploymentExecutor` 仍会把完整配置正文保存到 `server_config`。

`server_config` 同时被多个流程借作运行状态索引：

- `TrafficStatsTask` 通过表记录决定需要采集流量的服务器；
- `RateLimitService` 通过启用记录决定需要同步限速配置的服务器；
- `CoreConfigCleanupTask` 通过记录中的路径决定备份清理目录；
- 配置管理控制台允许编辑数据库配置正文并重新上传。

这些职责并不需要完整配置正文，而且数据库记录可能与远端实际运行状态不一致。完整配置还包含账户 UUID、协议参数和密钥类内容，不适合作为普通管理端 CRUD 数据长期保存和返回。

## Goals / Non-Goals

**Goals:**

- 删除完整 sing-box 配置正文的数据库持久化。
- 消除远端配置生效后因保存 `server_config` 失败而导致部署接口返回失败的问题。
- 让流量采集、限速同步和备份清理从服务器、节点及固定单内核约定推导目标。
- 删除允许绕过节点部署数据模型的手工配置编辑和重传入口。
- 保留动态配置预览、节点部署版本、远端配置校验、远端备份和节点部署状态更新。
- 删除 `server_config` 表及全部专用后端、前端和迁移代码。

**Non-Goals:**

- 不新增服务器级完整配置历史或配置正文归档。
- 不提供从数据库恢复最近一次服务器配置的能力。
- 不改变节点部署版本快照的结构和恢复行为。
- 不改变 sing-box 配置路径、远端备份命名和配置校验流程。
- 不引入新的服务器部署状态表。

## Decisions

### 1. 部署成功后不保存服务器级配置正文

`CoreDeploymentExecutor` 在远端配置上传、校验和重启成功后，只负责更新节点部署状态并记录节点部署版本。配置字符串仅存在于本次部署调用内，不进入数据库。

选择该方案是因为配置可以由当前业务数据确定性重建，远端文件才是实际运行产物。保留数据库副本会增加一致性边界，却不能保证其与远端状态同步。

备选方案是只删除 `config` 字段并保留 `server_config` 元数据。该方案仍让多个任务依赖一张人工维护的影子状态表，无法消除状态漂移，因此不采用。

### 2. 统一从有效服务器和已部署节点推导运行目标

流量采集与限速同步使用统一语义筛选服务器：

- 服务器未禁用；
- 服务器不是外部托管服务器；
- 服务器未过期；
- 服务器至少关联一个 `deployed = DEPLOYED` 且未禁用的节点。

系统为 sing-box 单内核，因此不再需要通过 `configType` 判断采集器或内核类型。

节点为 `PENDING_DEPLOY` 时，数据库状态代表变更尚未部署，不应单独使一台从未成功部署的服务器进入采集或限速同步集合。已有其他已部署节点的服务器仍正常参与任务。

### 3. 流量采集以服务器为执行单位

`TrafficStatsTask` 直接加载符合条件的服务器，每台服务器建立一次 SSH 连接并执行一次 sing-box gRPC 流量查询。`SingBoxTrafficStatsCollector` 删除未使用的 `ServerConfig` 参数。

这与当前单内核约束一致，也避免同一服务器因多条配置记录被重复采集。

### 4. 限速同步复用运行目标查询

`RateLimitService` 不再查询 `ServerConfigRepository`。全量同步从有效服务器集合中筛选存在已部署节点的服务器，单服务器同步使用同一判断。

同步时仍通过 `DeploymentDataLoader.loadForServer()` 重建完整配置并注入当前限速 override，不读取历史配置正文。

### 5. 备份清理使用固定 sing-box 路径

`CoreConfigCleanupTask` 遍历有效且存在已部署节点的服务器，并固定清理 `/etc/sing-box` 下符合 `config.json.backup.*` 的文件。

路径固定约定已经存在于 `SingBoxCoreManager` 和部署执行器，继续从数据库读取路径没有额外价值。

### 6. 删除配置管理控制台及 API

删除 `/vpn/server-config` 页面和 `/api/admin/server-configs/**` 接口。服务器配置预览继续使用服务器接口中基于 `NodeDeploymentService.previewServerConfigs()` 的动态预览能力。

不提供数据库配置重传替代接口。需要重新下发时，管理员应执行节点或账户部署，使配置基于当前业务数据重新生成。

### 7. 数据库迁移直接删除表

在所有代码依赖移除后执行：

```sql
DROP TABLE IF EXISTS server_config;
```

不迁移配置正文，也不创建归档表。删除此前新增的 `ServerConfigColumnMigration` 和 `LONGTEXT` 迁移 SQL，避免对即将删除的表执行无意义扩容。

## Risks / Trade-offs

- [无法从数据库查看最近一次完整配置] → 保留动态预览，并可通过远端文件读取实际运行配置；产品已确认不要求数据库查看能力。
- [无法一键重传旧配置正文] → 统一通过节点部署重新生成和下发当前正确配置，避免恢复过期账户或路由数据。
- [目标服务器推导语义错误可能导致漏采集] → 将“有效服务器且存在已部署启用节点”封装为明确仓库查询，并覆盖无节点、待部署、已部署、待删除、禁用和过期场景测试。
- [删除最后一个节点后服务器不再参与任务] → 删除部署成功时先下发不包含该节点的新配置，再物理删除节点；之后停止流量采集和限速同步符合预期。
- [升级过程中旧代码访问已删除表] → 发布顺序必须是先部署不再引用该表的新版本，再执行或由新版本执行删表迁移；禁止先手工删表后运行旧版本。
- [回滚到旧版本后缺少表] → 回滚前需重建空 `server_config` 表或使用包含兼容建表逻辑的旧版本；旧配置正文不可恢复，但可重新部署生成。

## Migration Plan

1. 增加基于服务器和节点状态的目标服务器查询及测试。
2. 迁移流量采集、限速同步和备份清理，不再注入 `ServerConfigRepository`。
3. 停止在部署成功后持久化 `ServerConfig`。
4. 删除配置管理 API、控制台页面和页面注册。
5. 删除实体、仓库、服务、DTO、转换器、反射注册及相关测试。
6. 删除 `ServerConfigColumnMigration` 和 `V2026061401__expand_server_config_column.sql`。
7. 增加并执行 `DROP TABLE IF EXISTS server_config` 数据库迁移。
8. 验证节点部署、账户部署、配置预览、流量采集、限速同步和备份清理。

## Open Questions

无。产品已确认不要求保存、查看或重传最近一次服务器配置正文。
