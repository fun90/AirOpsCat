## Context

当前账户可用节点由标签关系推导：账户绑定标签，节点绑定标签，订阅生成时通过标签交集得到账户可访问节点。节点自身只有一个 `accessHostId`，订阅中的连接地址最终来自节点部署快照、接入主机、服务器域名或服务器 IP。

本变更需要为“同一节点上的不同账户展示不同 DNS 完整域名”提供精确覆盖能力，但用户已明确该能力只影响订阅输出，不影响节点部署、不影响节点用户列表，也不改变标签授权主链路。

## Goals / Non-Goals

**Goals:**

- 支持为账户在指定节点上绑定一个订阅展示 DNS 完整域名。
- 保证同一账户在同一节点上最多只有一个 DNS 记录绑定。
- 绑定管理中只允许选择该账户通过标签授权得到的节点，并默认加载 20 条可选节点。
- 订阅生成时优先使用账户-节点绑定的 `domain_dns_record.full_name` 覆盖该节点的连接地址。
- 绑定缺失、禁用、DNS 记录不存在或 `full_name` 为空时保持现有订阅地址解析行为。
- 保持节点部署、节点用户列表、部署快照和远端配置生成不受影响。

**Non-Goals:**

- 不改变节点标签与账户标签的授权推导规则。
- 不让绑定触发节点重新部署。
- 不把绑定 DNS 完整域名写入节点部署快照。
- 不改变 DNS 记录管理、DNS 服务商绑定或证书申请流程。
- 不支持同一账户在同一节点上绑定多个域名。

## Decisions

### 1. 使用独立绑定表表达账户-节点-DNS 记录关系

新增 `account_node_subscription_domain_binding` 表，核心字段建议为：

- `id`
- `account_id`
- `node_id`
- `domain_dns_record_id`
- `enabled`
- `remark`
- `create_time`
- `update_time`

并建立 `account_id + node_id` 唯一约束。

理由：该关系既不属于账户基础信息，也不属于节点部署配置。独立表可以清晰表达“某账户在某节点上的订阅展示 DNS 完整域名”，并避免污染 `node` 或 `account` 表。

备选方案：

- 在 `node` 上保存账户域名映射 JSON：查询和唯一性校验困难，前端管理和后续扩展也不清晰。
- 在 `account` 上保存节点域名映射 JSON：同样缺少关系约束，且不利于按节点查看已绑定账户。
- 直接复用标签关系：标签表达授权集合，不适合承载账户级域名覆盖。

### 2. 绑定引用现有 `DomainDnsRecord` 记录

绑定表保存 `domain_dns_record_id`，订阅生成时读取 `DomainDnsRecord.fullName` 作为覆盖地址。前端搜索和保存也必须围绕 DNS 记录完整域名，不能直接搜索 `domain` 表。

理由：订阅覆盖需要使用实际可解析的完整主机名，`domain_dns_record.full_name` 能表达子域名、根域名等 DNS 记录级地址，避免只绑定主域名时无法区分同一域下多个订阅入口。

备选方案：

- 直接保存域名字符串：实现更简单，但会绕开 DNS 记录管理，产生重复数据。
- 绑定 `Domain.domain`：复用域名资产简单，但无法选择 DNS 记录完整域名，不满足本次要求。
- 同时支持 `domain_dns_record_id` 和自由文本域名：灵活但会增加校验、展示和优先级复杂度，首期不需要。

### 3. 订阅生成阶段执行地址覆盖

`SubscriptionService` 仍先通过现有 `TagService.getAvailableNodesByAccount(accountId)` 获取账户可用节点，并从部署快照构造 `NodeDto`。在返回订阅节点列表前，按账户 ID 和节点 ID 批量查询启用绑定，将匹配到的 `DomainDnsRecord.fullName` 写入订阅用 `NodeDto.serverHost`。

理由：覆盖只影响订阅展示地址，放在订阅 DTO 构造阶段最贴合需求，也能避免部署快照和远端配置被误修改。

备选方案：

- 在部署快照生成时写入账户域名：会破坏“只影响订阅”的边界，而且部署快照不是账户维度。
- 在模板中动态查询绑定：会把业务查询散落到模板渲染阶段，不利于维护和测试。

### 4. 节点用户列表继续由标签关系推导

`DeploymentDataLoader.buildNodeClientsMap` 和相关标签查询不读取账户-节点域名绑定。绑定只在订阅生成链路生效。

理由：用户已明确节点用户列表保持“节点标签 -> 账户标签”推导。这样也避免绑定变更导致远端配置需要刷新。

### 5. 管理接口采用账户或节点维度查询

建议新增后台 API，支持：

- 按账户查询绑定列表。
- 按节点查询绑定列表。
- 按账户查询可绑定节点列表，节点来源必须与订阅生成使用的标签授权节点集合一致，默认返回前 20 条并支持搜索过滤。
- 创建或更新某账户在某节点上的 DNS 记录绑定。
- 启用、禁用或删除绑定。

保存时必须校验账户、节点和 DNS 记录存在且 `fullName` 有效，同时校验节点属于该账户可用节点集合，并依赖唯一约束保证同一账户同一节点只有一条绑定。

## Risks / Trade-offs

- 绑定域名与节点实际入站证书/SNI 不匹配 -> 订阅可能生成可连接性不佳的地址；保存时可提示该能力只覆盖订阅地址，不保证证书或 DNS 已就绪。
- 绑定 DNS 记录被删除或 `fullName` 为空后订阅仍尝试覆盖 -> 查询绑定时必须只使用可解析到有效 `DomainDnsRecord.fullName` 的启用绑定，异常数据回退默认节点地址。
- 逐节点查询绑定导致订阅生成变慢 -> 按账户 ID 和节点 ID 列表批量加载绑定，再在内存中按 `nodeId` 匹配。
- 唯一约束冲突导致并发保存失败 -> 服务层先查后改，数据库唯一约束兜底，并把冲突转换为可读错误。

## Migration Plan

1. 新增绑定表和唯一索引，初始无数据，不影响现有订阅。
2. 部署后管理员可逐步为账户和节点配置域名绑定。
3. 回滚时删除订阅覆盖逻辑即可恢复旧行为；绑定表保留不会影响部署和标签授权。
