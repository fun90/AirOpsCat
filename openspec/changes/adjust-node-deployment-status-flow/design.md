## Context

节点部署目前以 `node.deployed` 的 0/1 值驱动多个流程：节点列表筛选、部署入口只选择未部署节点、部署成功后置为 1、订阅只读取已部署节点、配置变更和标签变更把节点置回 0。删除流程现在是 `NodeService.deleteNode` 直接物理删除，前端只在“已部署且已禁用”时显示删除入口，但后端没有“删除后等待远端刷新”的状态。

本次改动不引入新的部署系统，而是在现有 `deployed` 字段上建立三态模型，并调整部署数据加载与成功持久化逻辑，让远端配置刷新成为删除已部署节点的确认点。

## Goals / Non-Goals

**Goals:**
- 用明确状态表达节点是否需要部署、是否等待删除、是否已经部署完成。
- 删除已部署节点时先进入“待删除”，下一次部署成功后再物理删除。
- 保持订阅只暴露“已部署、未禁用、代理类型”的节点，不泄露待部署或待删除节点。
- 前端筛选、徽章、操作按钮和提示文案都使用三态名称。
- 用枚举或集中常量替代散落的 `0` 和 `1` 部署状态判断。

**Non-Goals:**
- 不重做部署任务调度、异步执行模型或 SSH 执行机制。
- 不新增节点回收站、撤销删除或审计日志。
- 不改变 `disabled` 的启用/禁用语义。
- 不迁移 `deployed` 字段名，除非实现时发现 ORM 或前端兼容成本明显更低。

## Decisions

### Decision: 保留 `node.deployed` 字段，使用枚举定义三态值

建议新增 `NodeDeploymentStatus` 枚举，映射如下：

- `0`：待部署
- `1`：已部署
- `2`：待删除

这样可以避免数据库迁移和历史数据转换。代码层通过枚举方法判断 `isPendingDeploy`、`isDeployed`、`isPendingDelete`，前端仍接收整数值，但展示和筛选使用三态标签。

备选方案：
- 新增 `deployment_status` 字段。语义更清晰，但需要迁移、兼容旧字段，并清理大量已有引用；本次需求可以先低风险落在现有字段上。
- 将状态改为字符串。可读性更好，但会影响现有数值筛选和排序，迁移成本更高。

### Decision: 已部署节点删除走“待删除 -> 部署刷新 -> 物理删除”

删除节点时根据当前状态分支：

- 待部署节点：尚未进入远端配置，可直接物理删除。
- 已部署节点：标记为待删除，返回“已标记待删除”。
- 待删除节点：保持幂等，返回当前状态。

部署配置构建时，待删除节点需要参与“本次部署需要处理的服务器集合”，但不能出现在新生成的 sing-box 配置中。部署成功后，属于本服务器的待删除节点再物理删除。

备选方案：
- 删除时立即触发一次强制部署。自动化更强，但删除 API 会变成远程操作，失败处理和响应时间都更复杂。
- 禁用节点代表待删除。会混淆“临时停用”和“准备移除远端配置”两个运维意图。

### Decision: 标准部署选择待部署和待删除节点，强制部署可包含已部署节点

普通部署应处理所有 `待部署` 和 `待删除` 节点，或处理指定 ID 中处于这两种状态的节点。强制部署继续允许对已部署节点刷新远端配置，但配置构建仍必须排除待删除节点。

节点组扩展逻辑也要使用三态：组内配置同步导致变更时标记为待部署；如果组内存在待删除节点，需要确保它所在服务器也进入部署刷新。

### Decision: 部署成功后的状态更新按节点状态分流

`CoreDeploymentExecutor.persist` 成功后应按节点状态处理：

- 待部署或强制部署的普通节点：置为已部署，并记录当前部署版本。
- 待删除节点：不记录新版本，清理相关标签关系、当前部署版本记录，再物理删除节点。
- 失败时不改变状态，让节点仍可重试。

这能保证“待删除”只有在远端配置刷新成功后才真正消失。

### Decision: API 保持兼容，同时增加三态筛选参数

当前列表接口使用 `deployed` 布尔查询参数。实现时建议新增 `deploymentStatus` 整数参数支持三态筛选，并在过渡期保留 `deployed=true/false`：

- `deployed=true` 等价于“已部署”。
- `deployed=false` 等价于“待部署”，不包含“待删除”。

前端改用 `deploymentStatus`，避免“未部署”继续覆盖待删除语义。

## Risks / Trade-offs

- [待删除节点未进入部署批次] -> 部署查询必须显式包含待删除状态，并根据节点服务器刷新配置。
- [配置构建误包含待删除节点] -> 数据加载或配置构建前统一过滤可部署节点，待删除只作为触发服务器刷新和成功后清理的对象。
- [物理删除破坏关联数据] -> 删除前明确清理 `node_tag`、当前部署版本记录等关联；如已有仓库方法不足，补齐窄范围删除方法。
- [前端旧参数混用] -> 过渡期保留布尔 `deployed` 参数，控制台切换到 `deploymentStatus`。
- [状态魔法数字继续扩散] -> 后端新增枚举，前端新增状态常量和格式化方法，改动点集中替换。

## Migration Plan

无需数据库结构迁移。发布后历史值继续有效：

- `deployed = 0`：待部署
- `deployed = 1`：已部署

新增的 `deployed = 2` 只由新删除流程写入。回滚时，如果存在 `2`，旧代码会把它当作“已部署之外的其他值”，前端可能显示为已部署或未部署不一致；因此回滚前建议先部署待删除节点完成清理，或执行一次手工修正。

## Open Questions

- 删除待部署节点是否仍然保留二次确认弹窗文案为“数据将无法恢复”，而删除已部署节点改为“标记待删除，部署成功后移除”。
- 批量部署按钮是否改名为“部署待处理节点”，以覆盖待部署和待删除两个状态。
- 是否需要在节点列表统计卡中单独展示“待删除”数量。
