## Context

当前用户和账户分别由 `UserController` 与 `AccountController` 创建。账户记录通过 `userId` 关联用户，因此管理员必须先离开账户页面创建用户，再回到账户页面检索用户并完成账户表单。账户新增表单的限制参数大多初始化为 `0` 或空值，与日常实际使用值不一致。

现有续期弹窗允许填写续费金额和付款方式：正金额会生成一条 `INCOME` 类型、关联 `account` 业务记录的交易流水，不填金额则仅更新到期时间。账户新增弹窗虽同样设置到期时间，却没有对应的首期金额与交易登记入口。

本变更横跨账户页面、请求 DTO、用户/账户/交易服务和标签关联，并要求用户、首个账户与可选首期交易不能只成功一部分。现有独立用户创建、账户创建和账户编辑流程必须继续可用，且不引入数据库迁移。

## Goals / Non-Goals

**Goals:**

- 在账户新增弹窗内完成“选择已有用户”或“创建新用户”两种关联方式。
- 通过一个后端事务原子创建新用户、首个账户及账户标签关联。
- 在开户时复用续期的金额、付款方式和收入流水语义，记录可选首期交易。
- 为每次打开或成功提交后重置的账户新增表单提供指定默认值。
- 复用账户编号、UUID、认证码、日期周期等现有默认和生成规则。
- 返回可定位新用户和新账户的结构化结果，并提供可展示的校验错误。

**Non-Goals:**

- 不删除用户管理页面或现有独立创建接口。
- 不修改已有账户的限制值，也不改变账户编辑弹窗的回显行为。
- 不把默认值下沉为数据库默认值，不改变非管理端调用现有账户接口时的语义。
- 不批量创建多个账户，不调整订阅、部署或限流执行规则。
- 不改变续期接口的交易规则，不为空金额或零金额创建交易流水。

## Decisions

### 1. 在账户新增弹窗提供两种用户关联模式

弹窗默认使用“创建新用户”模式，展示邮箱、密码、昵称和角色，不展示用户备注名与用户备注；管理员也可切换到“选择已有用户”模式并继续使用现有远程搜索组件。两种模式复用同一组账户字段，账号备注名紧跟账号字段展示并由前端校验为必填。

选择该方案是因为它把完整开户动作集中在管理员当前任务入口，同时不影响为已有用户追加账户。备选方案是在用户新增成功后自动跳转账户页，但仍涉及两次提交且无法保证原子性。

### 2. 使用专用组合请求与单一事务编排服务

新增组合创建端点，例如 `POST /api/admin/accounts/onboarding`，接收专用请求 DTO：用户关联模式、新用户资料或已有 `userId`、账户资料，以及可选的首期金额和付款方式。请求必须且只能指定一种用户来源；填写金额时必须为正数且付款方式必须属于现有 `PaymentMethod` 枚举。

编排服务使用一个 `@Transactional` 方法完成用户唯一性校验、用户持久化、账户持久化、标签关联和可选交易持久化；任何校验、唯一约束、标签关联或交易创建异常都让整个事务回滚。控制器只负责协议映射和错误响应，不在控制器中分段持久化。

选择专用端点而不是让浏览器连续调用两个现有接口，可避免第二次请求失败后遗留孤立用户。也不扩展现有 `POST /api/admin/accounts` 的多态请求，以保持原接口契约清晰和向后兼容。

### 3. 默认值由前端统一工厂初始化

在 `person/account.js` 定义创建表单默认值工厂，初次加载、打开新增弹窗和成功提交后的重置均通过同一工厂生成：

- `maxConnections = 100`
- `maxIps = 3`
- `bandwidth = 500`（GB）
- `downloadMbps = 20`
- `uploadMbps = 10`
- `level = 4`
- `nodeMultiple = 2`

日期、周期、节点前缀等现有默认逻辑继续保留。提交时发送管理员当前看到的值，后端不强制用默认值覆盖显式输入。

选择前端表单默认值而不是实体或数据库默认值，是为了只改变管理端交互，不意外影响 API 调用方、导入流程或历史数据。

### 4. 组合请求使用独立用户 DTO 并沿用服务层规则

新用户子对象只暴露允许开户填写的字段，不直接以 `User` 实体作为外部请求类型。服务层负责规范化邮箱、检查重复邮箱、应用角色/启用状态默认值及密码处理；账户子对象沿用 `AccountRequest` 的字段语义，并调用现有账户生成与校验逻辑。

新增请求/响应 DTO 必须加入 `JsonReflectionConfiguration`，确保 JVM 与原生镜像行为一致。响应返回 `UserDto`、`AccountDto` 和可空的 `TransactionDto`，避免直接泄露密码等实体字段，并让前端确认本次是否生成流水。

### 5. 首期交易复用续期流水语义

账户新增弹窗在到期时间附近展示“首期金额”和“付款方式”，交互规则与续期弹窗一致：金额留空时不创建流水；填写金额时必须为正数并选择合法付款方式。

新账户保存并取得 ID 后，事务编排服务创建收入交易：`type` 使用 `TransactionType.INCOME`，`businessTable` 为 `account`，`businessId` 为新账户 ID，金额与付款方式取管理员输入，备注沿用账户备注，描述标识为账号首期及对应有效期。首期有效期根据账户开始时间与到期时间计算，计算逻辑应与续期共用辅助方法，避免两处月份描述漂移。

选择复用同一种交易结构而不是引入“开户订单”表，是因为现有交易列表和统计已经按 `businessTable=account` 识别账户收入，且本需求只要求补齐与续期一致的流水记录。

### 6. 移动端账户操作使用表格外独立面板

账户表格位于横向滚动容器中，移动端公共样式还会为单元格设置 `overflow: hidden`。下拉菜单即使提高 `z-index`，仍无法越过祖先容器的裁剪边界。桌面端继续使用行内下拉菜单；移动端点击“操作”后打开位于表格容器之外的独立 Modal，完整展示同一组账户操作，并在选择操作前先关闭面板。

选择独立面板而不是放宽整个响应式表格的 `overflow`，可以保留横向滚动和列裁剪行为，也不会让宽表突破卡片或页面边界。

## Risks / Trade-offs

- [前端两种模式的隐藏字段被误提交] → 构造请求时仅序列化当前模式对应的用户字段，切换模式时清理相关校验错误。
- [组合服务调用已有异步限流同步时机早于事务提交] → 保持现有账户创建触发方式，并在测试中验证失败回滚不会产生可见账户；如同步组件读取未提交数据，应改为事务提交后触发。
- [并发请求绕过重复邮箱预检查] → 依赖数据库唯一约束作为最终防线，并把冲突转换为明确的 400/409 错误。
- [标签不存在导致开户失败] → 在同一事务中校验标签并整体回滚，前端保留输入并显示错误，便于修正后重试。
- [账户已创建但交易保存失败] → 将交易创建纳入同一事务，交易异常时回滚用户、账户和标签关联。
- [开户与续期的交易描述计算不一致] → 抽取共享的有效期描述或月份计算方法，并分别覆盖开户与续期测试。
- [默认值在多处复制后漂移] → 前端使用单一默认值工厂，测试同时覆盖初次打开和重置场景。

## Migration Plan

1. 先部署兼容的新 DTO、组合服务和端点，再部署使用该端点的前端资源。
2. 无数据库迁移；已有用户、账户和接口调用方无需处理。
3. 回滚时恢复旧前端并移除组合端点即可，已成功创建的数据仍是普通用户和账户，可由原有功能继续管理。
