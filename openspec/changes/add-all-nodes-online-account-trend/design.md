## Context

上一轮变更已经规划并实现了节点每日在线账户日统计、单节点趋势页面和节点列表中的单节点入口。当前需求进一步要求管理员可以在一个页面查看所有节点的趋势，从整体视角比较节点使用情况，减少逐个打开节点详情页的成本。

所有节点总览应建立在同一套 `node_online_account_daily_stats` 日统计数据之上，继续使用按 `accountNo` 去重的在线账户口径。前端应沿用控制台 Qute、Tabler、petite-vue 和 ApexCharts 的页面模式，避免引入新的可视化依赖。

## Goals / Non-Goals

**Goals:**

- 提供所有节点每日在线账户趋势总览页面。
- 支持近 7 天、近 30 天、近 90 天范围切换。
- 展示整体在线账户趋势、节点峰值排行或利用率对比，帮助管理员快速识别扩容和缩容候选节点。
- 提供从总览页进入单节点趋势页的路径。
- 复用已有日统计表、采样任务和去重口径。

**Non-Goals:**

- 不改变节点每日统计的采样逻辑和数据表结构。
- 不做自动扩容、自动缩容、容量预测或告警推送。
- 不回填历史统计数据。
- 不在总览页展示每个节点的连接明细；连接明细继续由现有在线详情处理。

## Decisions

1. 总览页复用日统计表，不新增采集链路。

   - 方案：按查询天数读取 `node_online_account_daily_stats`，按日期聚合所有节点的每日去重账户数、峰值在线账户数，并按节点生成排行数据。
   - 理由：单节点趋势已经建立了稳定的日统计口径；总览页只需要换一种聚合方式。
   - 备选：直接查询 `account_online_ip` 当前在线表。该方案只能看到当前窗口，无法形成历史趋势，也会和单节点页面口径不一致。

2. 总览 API 使用独立端点，避免单节点端点职责膨胀。

   - 方案：在节点在线账户统计控制器中增加 `/api/admin/node-online-account-stats/overview/summary` 和 `/api/admin/node-online-account-stats/overview/charts?days=30`，或等价的 overview 子路径。
   - 理由：总览数据不绑定单个 `nodeId`，独立路径更清晰，前端也能并行请求摘要和图表数据。
   - 备选：让单节点 charts 接口接受空 `nodeId` 表示全部节点。该方案语义含糊，也容易破坏已存在的单节点契约。

3. 页面展示以“整体趋势 + 节点排行”为主。

   - 方案：总览页主图展示全节点每日去重在线账户数与全节点每日峰值在线账户数；摘要卡展示节点总数、有数据节点数、周期峰值、周期平均每日活跃账户。下方或侧栏展示节点峰值排行、低利用率节点列表，并提供跳转单节点趋势的入口。
   - 理由：管理员扩容时关注高峰节点，缩容时关注长期低使用节点；总览页需要先帮助筛选节点，再跳进单节点细看。
   - 备选：在一张图中画出所有节点的多条折线。节点较多时图表会拥挤，难以一眼判断。

4. 控制台入口放在节点管理页面。

   - 方案：在节点列表页面的工具区或页面操作区域增加“全部在线趋势”入口，跳转到 `/console/vpn/node-online-account-overview`。
   - 理由：这是节点管理相关的运营视图，入口放在节点列表最符合管理员工作流。
   - 备选：把页面放入左侧菜单。该页面频率介于列表和详情之间，后续如使用频率高可以再展示在菜单中。

5. 空数据状态必须可用。

   - 方案：当查询范围内没有日统计数据时，总览页展示空状态和说明，保留范围切换与返回节点列表入口。
   - 理由：新部署或刚升级后的实例可能还没有统计数据，页面不能表现为错误。

## Risks / Trade-offs

- 节点数量较多导致排行和图表数据过大 → API 默认只返回聚合趋势和有限数量排行，必要时前端提供 Top N 展示。
- 总览页刚上线时历史为空 → 页面展示空状态，并依赖后续采样逐步积累数据。
- 低利用率判断可能受采样天数影响 → 页面允许切换 7/30/90 天，并在摘要中展示所选周期。
- 多节点聚合时同一账号跨多个节点会被重复计入整体活跃账户 → 总览页聚合的是“节点承载账户数”，用于容量视角；不把它解释为全站唯一账号数。

## Migration Plan

- 无需新增数据库迁移；继续使用已有节点在线账户日统计表。
- 发布后页面会读取已有统计数据；无历史数据时展示空状态。
- 回滚时移除总览页面入口、总览 API 和相关 DTO，不影响单节点趋势统计和采样任务。
